# Product mapping

**Prototype:** `design/scripts/screens/product-mapping.js` · **Suggested route:** `/app/product-mapping`

## Why this page exists
A filter row only says "attachment X fits Make / Year / Model". The attachment is the product SKU from the merchant's CSV (SKU only, agreed 2026-10-09: no product links, handles or collection links). To show anything to shoppers, SpareFit must know **which product in the store** that text means:
- **Search results** need the real product (title, image, price, Add to cart). An unlinked row can't be shown.
- **The Fits badge** sits on a product page; it can only answer "does this fit?" if that product is linked to rows.
- **The reverse problem**: a product with no rows never appears in any search, even if it fits everything.

Most links are made automatically on import (the attachment matches a variant SKU). This page handles what's left: rows we couldn't match, products nothing points to, and products that fit everything.

**First visit (products not loaded yet):** the store's products are loaded in the background. The first two tab counts are hidden and both lists show an empty state with a spinner, "Loading your products from Shopify…" — "This takes a moment for big stores. The list fills in by itself." There is no "match by" setting here or in the import: a row always points to a product by SKU. The UI says **SKU** everywhere; `attachment` is only the column name in the database.

## Data / backend
- **Matching** (rule-based, `app/services/linking/relink.server.ts`) runs after every import (quick: against the cached products), on **Sync products** (full: reloads the catalog first) and when a row is added or edited in Filter data. Attachment → variant SKU only (upper/lower case and outer spaces ignored); links and handles match nothing. Several variants with the same SKU: active products first, then the oldest. Results in `product_links` (`method` auto/manual); Choose product writes ordinary (auto) SKU links. Manual links only exist from before 2026-10-09; matching never changes them.
- **Catalog cache** (`catalog_products`, `catalog_variants`): filled by a bulk operation (products + variants); kept fresh by `products/create|update|delete` webhooks, which queue a per-product job that reads the product again from the Admin API (late or out-of-order webhooks can't leave stale data). A deleted product's rows become unlinked, or link to another product with the same SKU.
- Page loader (`/app/product-mapping?u=&p=&x=`, the three page numbers): unlinked groups, products without filter data (active products that no link with rows behind it points to, and not universal), universal products. `GET /api/links/status` is polled while a check runs.
- Actions (route intents, zod-validated): `check`, `link` (`attachment`, `resourceId` product gid, optional `variantId`; the product is read from Shopify before linking), `universal-add` (`ids`), `universal-mark`, `universal-remove` (`productId`).

## Build notes
Plain Polaris. Matching is rule-based (no AI). Toasts for every action (Shopify toast).
