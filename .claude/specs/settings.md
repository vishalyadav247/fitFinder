# Settings

**Prototype:** `design/scripts/screens/settings.js` · **Suggested route:** `/app/settings`

## Purpose
App-wide settings that don't belong to one feature. There is no Labels or Translations section: storefront texts are written where they are used (placeholders on Search setup; the other texts on the Storefront tabs).

## Layout
Two tabs (agreed 2026-10-16), the Storefront page's segmented tab bar in its compact form (`.sp-tabs sp-tabs--compact`: as wide as its tabs, each at least 150px, not the page; icon per tab): **General** (sliders icon; default) and **Custom CSS** (code icon). The open tab is kept in the URL (`?tab=css`). General holds Store type, Your data and Help; Custom CSS holds the Custom CSS card. No list of class names (removed 2026-10-16, user).

1. **Store type** — current type + "Sets the starting fields and wording. Fields stay fully editable." + **Change** (`icon="store"`, → onboarding in change mode).
2. **Custom CSS** (its own tab; added 2026-10-16; plan feature `customCss`) — `SectionTitle` (icon `code`) "Custom CSS" + "Small style changes for SpareFit on your store: the search widget, Fits badge, fitment table and My Selection button. Your CSS only applies to SpareFit, so it can't change the rest of your theme."
   - `s-text-area` **CSS** (10 rows, max 5,000 characters, placeholder `.sp-sfw__go { text-transform: uppercase; }`), details "Up to 5,000 characters. @import, @font-face and other global rules are left out."
   - No Save button in the card (changed 2026-10-16, user): unsaved CSS opens the App Bridge **save bar** (Save / Discard, `discardConfirmation`), like the Storefront page; leaving from inside the page (Change store type) asks first. Save → toast "Custom CSS saved"; "Custom CSS saved. Your theme gets it shortly." when another publish is running and picks it up; error toast "Custom CSS saved, but your theme couldn't be updated. Save again to retry." when the publish failed. Other error toasts: "Use 5,000 characters or fewer." · "The CSS couldn't be saved. Try again."
   - Rules that were left out → dismissible warning `s-banner` "Some of your CSS was left out" — "Not used on your store: {list}. Only rules for SpareFit's classes, @media, @supports and @container work here."
   - Plan without the feature: a **locked layer** (`LockedSection`, agreed 2026-10-16): the content shows blurred and can't be used; on top a card with a gold badge "{plan} plan" (lock icon; "Higher plan" when no plan has it yet), "{Feature} is on the {plan} plan", one line, and primary **Upgrade to {plan}** (to Plans; "Compare plans" when none) over the editor ("Style SpareFit on your store with your own CSS."); the action refuses with "Your plan doesn't include custom CSS."
   - Scoping (`app/services/storefront/custom-css.ts`): a rule's selectors become `:is(ROOTS) :is(list), :is(list):is(ROOTS)` (forgiving, so one unknown selector can't drop the rest); selectors with a pseudo-element get their own rules with the root check before it; the CSS is read as browsers do (escapes, strings that end at a line break, brackets matched by kind) so a body can't hide a rule end and escape the scope; at most 20,000 characters are published, ROOTS = `.sp-search-wrap, .sp-results, .sp-dd__list, .sp-badge-wrap, .sp-table-wrap, .sp-ms`, so `body` or `h1` only match inside SpareFit. Only `@media`, `@supports` and `@container` are kept; `@import`, `@font-face`, `@keyframes`, other at-rules, nested rules and unsafe values (`expression(`, `javascript:`) are dropped; `<` is escaped. The raw CSS is stored in `storefront_settings.settings.customCss`; the scoped CSS is published as `css` in the app metafield config (only when the plan includes it) and printed by the app embed and each block as `<style data-sp-css>`. The admin Live previews apply it too.
3. **Your data** — plain explanation, no actions: what we store (search fields, filter rows, product links, the last {n} imported files ({n} = 5 with the Import backups feature), texts and settings); shoppers (My Selection lives in the shopper's browser; no names, emails or orders); backups (download the last {n} files from Search setup › Import history; without the Import backups feature, "your plan doesn't include import backups." and the files clause in "what we store" is left out); if you uninstall (search disappears at once, data kept 30 days, then deleted); privacy requests (Shopify GDPR webhooks handled automatically). Products in Shopify are never changed.
4. **Help** — no buttons (agreed 2026-10-15: support is a live chat widget on the right side of the app, added by a separate script). A short message: "Need a hand? Chat with our support team right here in SpareFit." and a list: click the **chat button** on the right side of the screen to start a conversation; ask anything (setting up your search, importing fitment data, linking products, adding SpareFit to your theme or your plan); messages stay in the chat, so you can close it and pick up the conversation later.
5. **Feedback** (added 2026-10-16, `specs/APP_REVIEW.md`) — `SectionTitle` (icon `star`) "Feedback"; text (subdued) "We value your feedback! It helps us make SpareFit better. Let us know how we're doing." + **Write a review** (`icon="star"`, right) → `https://apps.shopify.com/{handle}#modal-show=WriteReviewModal` in a new tab (`target="_blank"`: the App Store can't open inside the admin frame). The link comes from `APP_STORE_URL`; the whole section is hidden while that isn't a listing URL (unset, or the App Store search used before launch). Neutral wording only: never ask for a positive review or offer anything for one (Shopify's review rules).
6. *(Prototype only)* **Reset this prototype** — Restore sample rows · Start over (confirms first).

No notification settings: import results are shown during the import itself. No export here: Filter data has Export, and Import history has file backups.

## Data / backend
- **App Store review prompt** (all admin pages, not a Settings control): the app layout (`app/routes/app.tsx`) asks Shopify's own review modal with App Bridge `shopify.reviews.request()` once per app load (`ReviewPrompt`, inside `AppProvider`; a ref guard so revalidations don't ask again). Asked only when `isReviewPromptEligible` (`app/services/review.ts`): installed over 24 hours ago (`shops.installed_at`) **and** shoppers searched in the last 30 days (`search_stats`, a primary-key read; current state, so a store that took the search down isn't asked). Never on onboarding. No state of our own (no "last asked" column): Shopify enforces 60 days between shows, 3 a year and already-reviewed, and refuses otherwise; the refusal code is only logged (`console.debug "[reviews] not shown: {code}"`), the merchant sees nothing. No end date (agreed default 2026-10-16; Shopify's limits cap it at 3 a year). Skipped when the cached App Bridge has no Reviews API. Test on a development store (Shopify bypasses its limits there); to pass our 24-hour gate locally: `UPDATE shops SET installed_at = now() - interval '2 days' WHERE domain = '…'` (never in production).
- Uninstall: `app/uninstalled` webhook → mark shop; delete data after 30 days. Handle the mandatory GDPR webhooks (`customers/data_request`, `customers/redact`, `shop/redact`).
